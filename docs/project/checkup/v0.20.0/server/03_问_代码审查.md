# 后端代码审查（问）

日期：2026-05-14　版本：v0.20.0

## 审查范围

基于望（结构统计）和闻（静态分析）的发现，重点审查以下文件：
- 大文件 TOP 5（超过 400 行）
- warning 集中的模块（im-message 6 个、im-ws 3 个、flash-user 3 个）
- 跨模块的公共接口（flash-core）
- 错误处理一致性

---

## 模块依赖关系

```
flash-core（基础层，无内部依赖）
  ↑
im-conversation（依赖 flash-core）
  ↑
im-message（依赖 flash-core, im-conversation）
  ↑
im-ws（依赖 flash-core, im-message）
  ↑
im-group（依赖 flash-core, im-message, im-ws）
im-friend（依赖 flash-core, im-ws, im-conversation, im-message）
flash-user（依赖 flash-core）
app-storage（无内部依赖）
```

**结论：无循环依赖**，依赖方向清晰，从底层 flash-core → im-conversation → im-message → im-ws → im-group/im-friend。

## im-message（占比 17.0%，6 个 warning）

### routes.rs（601 行，4 个 warning）

**职责过多**。routes 层包含了大量业务逻辑：

| handler | 行数 | 问题 |
|---------|------|------|
| search_messages | ~80 行 | 多步 SQL 查询 + 结果组装，应下沉到 service |
| recall_message | ~70 行 | 校验 + 状态更新 + 预览刷新 + 广播，完整业务流程 |
| forward_message | ~60 行 | 校验 + 消息复制 + 广播 |
| get_read_status | ~40 行 | 多步查询 + 分组逻辑 |

routes 层应该只做：解析参数 → 调用 service → 返回响应。当前 recall/forward/pin 已经用了 `AppError`，但 get_messages/send_message/get_read_seq 还在返回 `StatusCode`。

**clippy warning**：
- `type_complexity`（第 202、250 行）：handler 的 Path 参数类型过长，建议用 type alias
- `manual_clamp`（第 158、244 行）：`limit.min(50).max(1)` 应改为 `.clamp(1, 50)`
- `single_component_path_imports`（第 9 行）：`use sqlx;` 冗余

**严重程度**：🟡 一般。分层不清晰，但功能正确。

---

### service.rs（208 行）

**`send_inner` 和 `send_system` 有大量重复代码**：

两个方法都执行了相同的流程：
1. 生成 seq
2. 存储消息
3. 生成预览
4. 更新会话 last_message
5. 给其他成员 unread +1
6. 获取成员列表
7. 广播消息 + 广播会话更新

`send_system` 只是跳过了成员校验和群解散检查。可以抽取公共的 `_persist_and_broadcast` 方法。

**严重程度**：🟡 一般。重复代码增加维护成本。

## im-group（占比 23.9%，1 个 warning）

### routes.rs（527 行）

**routes 层直接写 SQL**。几乎每个 handler 都有查询用户昵称的 SQL：

```rust
let creator_name: String = sqlx::query_as::<_, (String,)>(
    "SELECT COALESCE(nickname, '?') FROM user_profiles WHERE account_id = $1"
)
.bind(user_id)
.fetch_optional(state.service.db())
...
```

这段代码在 `create_group`、`join_group`、`add_members`、`remove_member_handler`、`leave`、`transfer_owner`、`update_announcement`、`update_group` 中重复出现了 **10+ 次**。

**建议**：在 service 层或 repository 层提供 `get_nickname(user_id) -> String` 方法，routes 层只调用。

**严重程度**：🟡 一般。大量重复代码，但不影响功能。

---

### repository.rs（559 行）

方法数量多（20+ 个），但每个方法职责单一（一个 SQL 查询），结构清晰。

**`get_group_info` 返回值类型过长**：

```rust
pub async fn get_group_info(...) -> Result<Option<(Option<String>, Option<String>, Option<i64>, i64, bool, i16, Option<String>, Option<chrono::DateTime<chrono::Utc>>)>, sqlx::Error>
```

8 元素的元组可读性差，应定义一个 `GroupInfoRow` 结构体。

**严重程度**：🟢 轻微。可读性问题。

---

### service.rs（485 行）

**错误处理不一致**。同一个文件中混用两种模式：

| 方法 | 返回类型 | 错误处理 |
|------|---------|---------|
| create_group | `Result<..., StatusCode>` | `.map_err(|e| { println!(...); StatusCode::... })` |
| add_members | `Result<..., AppError>` | `?` 自动传播 |
| remove_member | `Result<..., StatusCode>` | `.map_err(|_| StatusCode::...)` |

按项目规范，应统一为 `Result<..., AppError>` + `?` 传播。

**严重程度**：🟡 一般。违反错误处理规范，且 `map_err(|_| ...)` 丢弃了错误详情。

## im-ws（占比 14.6%，3 个 warning）

### dispatcher.rs（277 行，2 个 warning）

**`too_many_arguments`**：
- `notify_group_join_request`：9 个参数
- `notify_friend_request`：7 个参数（加上 `&self` 是 8 个）

建议将通知参数封装为结构体：

```rust
pub struct GroupJoinNotifyParams {
    pub to_owner_id: i64,
    pub request_id: String,
    pub conversation_id: String,
    // ...
}
```

**严重程度**：🟢 轻微。参数多但语义清晰。

---

### state.rs（1 个 warning）

**`new_without_default`**：`WsState::new()` 存在但没有实现 `Default` trait。加一行即可：

```rust
impl Default for WsState {
    fn default() -> Self { Self::new() }
}
```

**严重程度**：🟢 轻微。

## flash-user（占比 5.0%，3 个 warning）

### handler.rs（306 行）

**`collapsible_if`**（2 处）：嵌套的 if 可以合并。

**`manual_clamp`**（1 处）：`limit.min(50).max(1)` 应改为 `.clamp(1, 50)`。

**错误处理全部返回裸 `StatusCode`**，无错误消息。用户收到 400/404/500 时无法知道具体原因。

**严重程度**：🟡 一般。

## im-friend（占比 11.2%，2 个 warning）

### repository.rs（2 个 warning）

**`type_complexity`**（第 89、123 行）：`get_received_requests` 和 `get_sent_requests` 的中间类型过长（9 元素元组）。应定义中间结构体。

### api.rs — 未使用 AppError

`im-friend` 有自己的 `FriendError` 类型，通过 `err_response` 辅助函数转换为 `(StatusCode, Json<...>)`。这与项目的 `AppError` 规范不一致。

**建议**：让 `FriendError` 实现 `Into<AppError>`，handler 统一返回 `Result<..., AppError>`。

**严重程度**：🟡 一般。

## 跨模块问题

### 1. 错误处理不统一（系统性问题）

| 模块 | 错误类型 | 是否符合规范 |
|------|---------|-------------|
| im-message/routes（recall/forward/pin） | AppError | ✅ |
| im-message/routes（其余） | StatusCode | ❌ |
| im-group/service | 混用 StatusCode + AppError | ❌ |
| im-group/routes | 混用 StatusCode + AppError | ❌ |
| im-friend/api | 自定义 FriendError | ❌ |
| flash-user/handler | StatusCode | ❌ |
| im-conversation/routes | StatusCode | ❌ |

只有 im-message 的新增 handler（recall/forward/pin）完全遵循了 AppError 规范。

### 2. "查昵称"代码重复

至少 15 处出现了相同的 SQL 模式：
```rust
sqlx::query_as::<_, (String,)>(
    "SELECT COALESCE(nickname, '?') FROM user_profiles WHERE account_id = $1"
)
```

应抽取为 `flash-core` 或 `flash-user` 中的公共方法。

### 3. println! 用于日志

后端使用 `println!` 输出日志（带 emoji 前缀如 📢、❌、📨）。在单进程开发阶段可以接受，但后续应引入 `tracing` crate 实现结构化日志。
